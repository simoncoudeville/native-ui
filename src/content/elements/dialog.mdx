`<dialog>` has been widely available for years, but it always came with a
caveat: you had to reach into JavaScript to call `showModal()` and `close()`.
The Invoker Commands API removes that last step. A button with `command` and
`commandfor` names the element it acts on and the action it performs, and the
browser wires up the rest, including keyboard behaviour and focus.

Every demo on this page is static HTML and CSS. There is no JavaScript on the
page driving any of them.

## Modal dialogs

`command="show-modal"` is the declarative form of `showModal()`. The dialog
gets promoted to the **top layer**, the rest of the page becomes inert, and a
`::backdrop` pseudo-element appears behind it.

## Animating a dialog

A dialog is harder to animate than an ordinary box. Opening it moves the
element from `display: none` to displayed and from outside the top layer to
inside it, and both of those are discrete: they flip rather than interpolate.
A plain `transition: opacity 0.2s` therefore gives an entry that never runs and
an exit that is cut off at its first frame. Three additions fix that.

`transition-behavior: allow-discrete` makes the flipping wait. Listed against
`display`, it keeps the element rendered for the length of the transition
rather than removing it at once. In the `transition` shorthand it is written as
a keyword after the property and duration.

`@starting-style` supplies the values to animate *from*. An element that was
`display: none` has no previous style to interpolate from, so without it the
dialog arrives at full opacity and only the exit animates.

Only `display` gets held back like that. Anything else in the `[open]` rule
reverts as soon as the dialog closes, so a `place-items` or a `gap` declared
beside `display: grid` is gone while the box is still visible, and the contents
jump during the fade. Keep those on the base rule and leave `[open]` to
`display` and the animated values.

`overlay` tracks whether an element is in the top layer. The browser sets it
and transitioning it is the only thing an author can do with it. With
`allow-discrete` it holds the dialog in the top layer until the exit finishes,
instead of dropping it out on the first frame.

| Piece                                 | Support                                            |
| ------------------------------------- | -------------------------------------------------- |
| `transition`                          | <BaselineBadge featureId="transitions" />          |
| `transition-behavior: allow-discrete` | <BaselineBadge featureId="transition-behavior" />  |
| `@starting-style`                     | <BaselineBadge featureId="starting-style" />       |
| `overlay`                             | <BaselineBadge featureId="overlay" />              |

`::backdrop` is a separate element as far as animation goes, so it needs its
own `transition`, its own `@starting-style` and its own `allow-discrete`
entries. Animating the dialog alone leaves the dim behind it snapping in and
out. The same three pieces drive the [popovers](/elements/popover/) on the next
page.

## Non-modal dialogs

`show()` opens a dialog in place. There is no backdrop, no focus trap, and the
rest of the page stays interactive. That is closer to an inline panel than an
overlay.

There is no command for it. The `command` attribute understands `show-modal`,
`close` and `request-close` for dialogs, and nothing that maps to `show()`, so
opening a non-modal dialog still takes a line of script. That is why there is
no demo of one on this page. Closing works either way, and a popover is the
closer fit for a panel that should open declaratively.

## Top layer, proven

This is the demo that justifies rendering everything inline instead of in an
iframe. The dialog below lives inside a bordered, padded card in the middle of
this page, and opens at the full size of your viewport.

<Demo
  name="fullscreen"
  html={fullscreenHtml}
  css={fullscreenCss}
  caption="Sized with 100vw / 100dvh. Its container cannot clip it, because it is no longer painted inside it."
/>

No `position: fixed`, no `z-index`, no portal. A modal dialog is moved to the
top layer, which sits above the entire document and outside every stacking
context on the page. Put that same dialog in an iframe and `100dvh` would mean
the height of the iframe. The effect disappears completely.

## Gotchas

<DerivedGotchas featureId="dialog-closedby" />

<Gotcha
  title="closedby has no Safari support yet"
  kind="quirk"
  staleWhen={{ feature: 'dialog-closedby', browser: 'safari', supported: true }}
>
  Safari ignores the attribute entirely. A modal dialog there still closes on
  Escape (that is `<dialog>`'s built-in behaviour, not `closedby`), so
  `closerequest` degrades perfectly. The one that genuinely differs is
  `closedby="any"`. Safari users get no light dismiss, so never rely on
  clicking the backdrop as the *only* way out. Always ship a visible close
  button, which you want for accessibility regardless.
</Gotcha>

<Gotcha
  title="Invoker commands are still new"
  kind="polyfill"
  staleWhen={{ feature: "invoker-commands", baseline: "high" }}
>
  `command` / `commandfor` reached Baseline in December 2025, so anyone on a
  browser more than a release or two old won't have it, and the buttons will do
  nothing at all. That is a hard failure rather than a graceful one. The
  [invokers polyfill](https://github.com/keithamus/invokers-polyfill) fills the
  gap and is small enough to load conditionally behind a `if (!('command' in
  HTMLButtonElement.prototype))` check.
</Gotcha>

<Gotcha
  title="overlay is the one piece of the animation that isn't Baseline"
  kind="quirk"
  staleWhen={{ feature: "overlay", baseline: "low" }}
>
  A browser that doesn't know the property drops it from the transition list
  and runs everything else, so the dialog still fades out. It leaves the top
  layer as it closes instead of when the fade ends, so the exit is painted in
  normal document order, where content that follows the dialog can cover it.
  Short exits make that repaint hard to catch. Nothing else about the dialog
  changes.
</Gotcha>

<Gotcha title="Give focus somewhere sensible" kind="a11y" evergreen>
  When a modal opens, focus moves into the dialog, but where it lands is your
  call. Put `autofocus` on the safest control, not the most destructive one: on
  a delete confirmation that means Cancel, so an accidental Enter doesn't
  destroy anything. On close, focus returns to the invoking button
  automatically, which is a genuine advantage over a hand-rolled modal where
  this is the step everyone forgets.
</Gotcha>

<Gotcha title="A dialog is not automatically a labelled region" kind="a11y" evergreen>
  Screen readers announce the dialog role, but the accessible name comes from
  you. Point `aria-labelledby` at the dialog's heading, or set `aria-label`.
  Also resist `role="dialog"` on the element itself. `<dialog>` already carries
  it, and re-declaring it is noise.
</Gotcha>

<Gotcha title="method=dialog forms still have a place" kind="quirk" evergreen>
  `command="close"` closes the dialog but sets no return value. If you need to
  know *which* button dismissed it, a `<form method="dialog">` with
  `<button value="confirm">` still sets `dialog.returnValue`. The two
  mechanisms coexist, and the form approach predates invokers by years.
</Gotcha>
